# 双板 CAN 通信周期性丢失问题排查记录

## 1. 问题背景

机器人采用云台板和底盘板双板架构，两块控制板通过 CAN 总线交换控制数据。

本次涉及的板间通信配置为：

| 方向 | CAN ID | 数据内容 |
| --- | --- | --- |
| 底盘板 → 云台板 | `0x311` | `Chassis_Control_Data_s` |
| 云台板 → 底盘板 | `0x312` | `Chassis_Ctrl_Cmd_s` |

由于 `Chassis_Control_Data_s` 加上包头、长度、CRC 和包尾后超过了单帧经典 CAN 的 8 字节限制，`CANCommSend()` 会将一个逻辑包拆成两帧发送：

- 第一帧：DLC = 8；
- 第二帧：DLC = 7。

云台板配置了约 100 ms 的通信守护超时。当 100 ms 内没有成功解析出一个完整逻辑包时，系统认为底盘通信丢失，执行急停并播放报警音乐。

## 2. 故障现象

增加通信失能报警后发现，机器人运行过程中大约每十几秒会播放一次通信丢失音乐。通信并不是永久断开，而是周期性地短暂进入异常状态，随后又能恢复。

主要现象如下：

- 云台板周期性判断 `0x311` 通信离线；
- 每次异常期间可能连续多次进入超时回调；
- 大多数时间仍然可以收到数据，并非 CAN 总线完全断开；
- 关闭调试断点后问题仍然存在；
- 仅凭原有 RTT 日志无法判断问题发生在发送、接收还是组包阶段。

## 3. 初始排查方向

最初考虑过以下可能：

1. Ozone 断点或 RTT 大量输出影响了任务实时性；
2. 云台板 CAN 接收回调每次只处理一帧，没有及时排空硬件 FIFO；
3. 云台板接收 FIFO 溢出；
4. `CANComm` 的分包、组包或 CRC 校验存在错误；
5. 底盘板发送 FIFO 已满，导致第二帧没有成功入队；
6. CAN 位时序、物理线路或总线错误导致报文丢失；
7. 报文虽然写入了底盘 FDCAN 发送 FIFO，但没有真正发送到总线。

为了区分这些情况，需要同时观察数据在以下几个层级中的状态：

```text
底盘应用层调用发送
    → 底盘 FDCAN 发送 FIFO
    → CAN 物理总线
    → 云台 bxCAN 接收 FIFO
    → 云台 CAN 接收回调
    → CANComm 组包和校验
    → 通信守护 Daemon
```

## 4. 建立独立 RTT 数据通道

原有日志全部输出在 RTT Terminal 0，其中包含电机、BMI088、任务延迟和普通告警等大量信息，不适合直接导出并进行数据分析。

因此新建 RTT Terminal 1，专门输出固定格式的 CSV 调试数据：

- Terminal 0：保留原有 `LOGINFO`、`LOGWARNING`、`LOGERROR`；
- Terminal 1：只输出 CAN 排查数据。

这里使用的是 **J-Link RTT Viewer**，而不是 J-Scope。J-Scope主要用于读取符号或 RAM 变量并绘制波形；本次需求是读取独立 RTT Up Channel 的文本数据，因此 RTT Viewer 更合适。

## 5. 云台板调试数据

云台板在三个位置增加计数：

### 5.1 原始 CAN 接收层

在 `CANFIFOxCallback()` 中统计：

- `0x311` 原始接收帧总数；
- DLC8 帧数量；
- DLC7 帧数量；
- 其他 DLC 数量；
- 最后一帧的接收时间；
- CAN FIFO 溢出信息。

### 5.2 CANComm 解析层

在 `CANCommRxCallback()` 中统计：

- 正确包头数量；
- 完整逻辑包数量；
- 校验成功数量；
- 错误包头数量；
- 长度错误数量；
- 接收缓冲区长度溢出数量；
- CRC 错误和包尾错误数量。

### 5.3 通信守护层

在 `CANCommLostCallback()` 中统计：

- 超时回调次数；
- 独立通信丢失事件次数；
- 最近一次超时时间；
- 当前组包状态和守护计数。

所有变量每 20 ms 输出到 RTT Terminal 1，之后由 RTT Viewer 保存为日志文件。

## 6. 云台板日志分析

在修改接收回调后导出的最新日志 `4.log` 中，选取约 89.68 秒的数据，累计变化如下：

| 计数项 | 增量 |
| --- | ---: |
| 原始 `0x311` 接收帧 | 31141 |
| DLC8 | 16625 |
| DLC7 | 14516 |
| 完整且校验正确的逻辑包 | 12191 |
| 错误包头 | 2325 |
| 组包长度溢出 | 2202 |
| 超时回调 | 277 |
| 独立超时事件 | 49 |
| CRC 错误 | 0 |
| 包尾错误 | 0 |

日志中的计数满足以下关系：

```text
raw_rx = dlc8 + dlc7 + other
dlc8   = header_ok + overflow
dlc7   = full_packet + bad_header
```

这说明计数链路本身是完整的，问题不是统计错误。

最关键的现象是：**DLC8 与 DLC7 的接收数量长期不相等，而且 DLC7 明显更少。**

正常情况下，一个逻辑包必须恰好包含一帧 DLC8 和一帧 DLC7。如果任意一帧丢失，原有状态机又没有包序号和分片序号，就会出现以下错位：

```text
收到包 A 的 DLC8
    → 包 A 的 DLC7 丢失
    → 收到包 B 的 DLC8
    → 被当成包 A 的第二帧
    → 接收长度超过预期，触发 overflow 并复位
    → 随后收到包 B 的 DLC7
    → DLC7 第一个字节不是包头，触发 bad_header
```

因此，`bad_header` 和 `overflow` 主要是前面发生丢帧后的连锁结果，不是发送数据内容或 CRC 本身出错。

对超时时间进行分析后还发现：

- 故障以时间簇形式出现；
- **相邻故障簇间隔约 19.5 秒；**
- **每个故障簇持续约 2 秒；**
- 异常期间 DLC7 的到达率下降尤其明显。

## 7. 验证“接收回调只读取一帧”的假设

原始 `CANFIFOxCallback()` 在找到对应 CAN 实例并执行回调后直接 `return`：

```c
can_instance[i]->can_module_callback(can_instance[i]);
return;
```

这样一次接收中断只处理一帧，即使 FIFO 内还有其他报文也会立即退出。为验证它是否为根因，将其修改为：

```c
can_instance[i]->can_module_callback(can_instance[i]);
break;
```

`break` 只退出实例查找循环，外层 `while` 会继续读取当前 FIFO，直至 FIFO 为空。

修改后重新烧录并导出 `4.log`，结果仍然出现：

- DLC8/DLC7 数量不相等；
- 大量 `bad_header` 和 `overflow`；
- 约 19.5 秒一次的通信丢失。

因此可以得出结论：

> 原来的 `return` 确实不利于及时排空 FIFO，改成 `break` 是合理改进，但它不是本次周期性通信丢失的根因。

## 8. 底盘板发送侧调试

随后在底盘板建立同样的 RTT Terminal 1 数据通道，对实际使用的 FDCAN3、发送 ID `0x311` 进行统计。

统计内容包括：

- 逻辑包发送调用次数；
- DLC8/DLC7 入队尝试和成功次数；
- 两帧入队前后的发送 FIFO 空闲数量；
- FIFO 等待超时次数；
- `HAL_FDCAN_AddMessageToTxFifoQ()` 错误次数；
- FDCAN 的 `TXFQS`、`PSR`、`ECR`、`ErrorCode` 和 HAL 状态。

约 97.44 秒的底盘日志结果如下：

| 计数项 | 结果 |
| --- | ---: |
| 逻辑包发送尝试 | 19488 |
| 两帧均成功写入 FIFO | 19488 |
| 部分入队失败 | 0 |
| DLC8 入队失败 | 0 |
| DLC7 入队失败 | 0 |
| FIFO 无空闲位置 | 0 |
| FIFO 等待超时 | 0 |
| HAL 添加报文错误 | 0 |

发送 FIFO 通常仍有 2～4 个空闲元素，也没有出现 Bus-Off 或明显的错误计数。

这些数据排除了“底盘软件发送过快、发送 FIFO 已满、第二帧无法写入”的假设。

但是，这里出现了一个关键认识：

> `HAL_FDCAN_AddMessageToTxFifoQ()` 返回成功，只能证明报文成功写入 FDCAN 发送 FIFO，不能证明它已经在物理总线上发送成功。

之前的调试计数将“两帧成功入队”命名为 `packet_ok`，它表示软件入队完整，不等于对端一定收到完整逻辑包。

## 9. 根因定位

继续检查底盘板 FDCAN3 初始化配置，发现：

```c
hfdcan3.Init.AutoRetransmission = DISABLE;
```

也就是 FDCAN3 关闭了自动重发。

底盘板的 FDCAN3 连接到云台板 CAN1，而云台 CAN1 上同时存在电机控制和反馈报文。CAN 通过报文 ID 进行无损仲裁，数值越小的 ID 优先级越高。板间通信使用的 `0x311` 优先级低于总线上的部分电机报文，因此可能在发送时竞争失败。

当自动重发关闭时，报文在仲裁或发送过程中未成功完成后，不会由控制器自动重新尝试。应用层看到的仍然可能只是“成功写入发送 FIFO”，而云台板实际上没有收到该帧。

一个逻辑包包含连续入队的两帧，第二帧 DLC7 更容易受到后续总线竞争影响。这与云台日志中“DLC7 比 DLC8 缺失更多”的现象一致。

完整故障链路为：

```text
底盘调用 CANCommSend()
    → DLC8、DLC7 均成功写入 FDCAN3 发送 FIFO
    → 0x311 与更高优先级报文竞争总线
    → FDCAN3 自动重发关闭
    → 部分分片未真正发送成功
    → 云台收到的 DLC8 和 DLC7 不成对
    → CANComm 组包状态机错位
    → 出现 overflow 和 bad_header
    → 100 ms 内没有完整有效包
    → Daemon 判断通信失能
    → 急停并播放报警音乐
```

## 10. 最终修复

仅修改底盘板板间通信所使用的 FDCAN3：

```c
// 修改前
hfdcan3.Init.AutoRetransmission = DISABLE;

// 修改后
hfdcan3.Init.AutoRetransmission = ENABLE;
```

修改位置：

```text
agv_chassis_mc02/Core/Src/fdcan.c
MX_FDCAN3_Init()
```

使用项目 Makefile 重新编译：

```sh
mingw32-make -j12
```

将新固件烧录到底盘板后，周期性通信失能和报警音乐现象消失，确认本次故障由 FDCAN3 关闭自动重发导致。

## 11. 为什么这个问题容易误判

### 11.1 入队成功不等于发送成功

HAL 发送接口返回成功时，数据通常只是进入了控制器的发送 FIFO。如果只统计 API 返回值，会误以为发送链路完全正常。

### 11.2 解析错误不一定是解析代码的根因

云台端出现大量包头错误和长度溢出，看起来很像组包状态机有问题。实际上状态机是在处理已经缺少分片的数据流，解析错误是丢帧造成的后果。

### 11.3 仲裁失败不一定表现为明显的总线故障

CAN 仲裁本身属于正常机制，不等同于 CRC 错误、Bus-Off 或物理层损坏。仅观察 `ErrorCode` 和错误计数，不一定能直接发现低优先级报文没有完成发送。

### 11.4 相同 CAN ID 的分片难以重新同步

当前两帧使用相同 CAN ID，协议内又没有包序号和分片序号。丢失任意一帧后，接收端只能根据包头和固定长度尝试重新同步，容易连续产生多个解析错误。

## 12. 后续改进建议

### 12.1 CAN/FDCAN 配置

- 正常需要可靠传输的经典 CAN 通信应默认开启自动重发；
- 修改 CubeMX 配置时同步检查生成代码，避免重新生成后恢复为 `DISABLE`；
- 评估板间通信 ID 的仲裁优先级；
- 评估总线负载，为控制和电机报文保留足够余量。

### 12.2 发送侧诊断

- 区分“应用调用”“成功入队”“发送完成”和“发送取消”；
- 必要时打开 FDCAN Tx Event、发送完成和发送取消中断；
- 记录仲裁丢失、错误计数、Bus-Off 和发送取消原因；
- 调试变量命名避免将“入队成功”直接称为“发送成功”。

### 12.3 通信协议

- 给逻辑包增加包序号；
- 给每个 CAN 分片增加分片索引；
- 接收端检测到新包头时允许快速重新同步；
- 为未完成逻辑包增加独立的短超时，避免错误状态保留过久；
- 对控制命令考虑使用单帧协议或两个不同 CAN ID，减少分片错位风险。

### 12.4 接收侧实现

- 接收中断中排空对应 FIFO；
- 对 CAN 过滤器配置结构体先清零再赋值；
- 独立统计 FIFO Full、FIFO Overrun 和硬件错误；
- 不在高频中断内执行耗时日志输出。

### 12.5 调试工具

- 保留 RTT Terminal 1 作为独立 CSV 调试通道；
- 普通日志和数据采样不要混用同一个 RTT Channel；
- 数据分析时优先使用累计计数器和时间戳，避免日志打印频率影响判断；
- 对通信链路分层计数，逐层确定数据在哪里消失。

## 13. 本次排查得到的通用方法

面对“通信偶发丢失”问题，不应只在最终超时位置增加日志，而应沿着数据链路分层验证：

1. 发送任务是否按预期调用；
2. 所有分片是否成功进入发送 FIFO；
3. 控制器是否报告发送完成或取消；
4. 接收控制器是否收到对应 ID 和 DLC；
5. 接收回调是否处理了全部报文；
6. 组包、CRC 和包尾校验在哪一步失败；
7. 通信守护为什么没有被及时重载。

只有把“软件入队”和“物理发送”分开，才能避免被表面正常的 HAL 返回值误导。

## 14. 结论

本次周期性通信失能不是由 RTT 日志、Ozone 断点、CANComm CRC、接收回调只读一帧或发送 FIFO 已满直接造成的。

最终根因是：

> 底盘板 FDCAN3 关闭了自动重发。板间报文 `0x311` 在共享 CAN 总线上发生竞争后，部分分片没有重新发送，导致云台端两帧逻辑包不完整，最终触发 100 ms 通信守护超时。

将 FDCAN3 的 `AutoRetransmission` 设置为 `ENABLE` 后，问题解决。
